◢ COUNCIL

Setup Guide: the manual, human-only steps. Everything else runs in code. Updated 2026-06-19.

Read first: the profit-margin reality.
Profit = trading edge minus (Kalshi fees + model cost). Self-hosting the models only touches the cost term, and at this project's scale it makes cost worse, not better: a rented GPU fleet only beats API pricing past roughly 240M tokens/day, far above what a trading council uses. Start with Path A. Path B exists only because you asked; treat it as an experiment.

Path A · Hosted APIs via OpenRouter RECOMMENDED

One account, one key, all three models (Claude + Kimi K2 + GLM-5.2), unified billing. About 15 minutes.

  1. Sign up at openrouter.ai.
  2. Add a small prepaid balance (e.g. $20) under Settings → Credits. This is your hard ceiling; you can't be billed past it.
  3. Keys → Create Key, then copy the sk-or-... value (shown once).
  4. Put it in ~/council/.env as OPENROUTER_API_KEY=sk-or-... (see the .env table).
  5. On the OpenRouter Models page, confirm the exact slugs for Claude, Kimi K2, and GLM-5.2 and tell me; I'll set them in config.yaml (mine are placeholders).
That's the whole setup for going live. Then I run python scripts/check_connectivity.py to confirm the models respond.

Path B · Self-host GLM-5.2 on a rented GPU OPTIONAL · ADVANCED

Honest cost warning.
A production GLM-5.2 (744B MoE) needs a multi-GPU box (several H100/H200). On-demand that's roughly $12k–30k/month if left running, and a cold start loads hundreds of GB of weights before the first token. This will not lower your trading costs at realistic volume. Kimi K2 (1T params) is impractical to self-host; keep Kimi on its hosted API even if you self-host GLM.
  1. Rent a box on a GPU marketplace (SimplePod, Vast.ai, or RunPod) with enough total VRAM for GLM-5.2 at FP8/INT4. Enable persistent storage so weights don't re-download on every restart.
  2. Serve it with an OpenAI-compatible endpoint (vLLM): 
    pip install vllm
vllm serve zai-org/GLM-5.2 \
  --tensor-parallel-size <#GPUs> \
  --api-key "choose-a-secret" \
  --port 8000
    (Exact HF repo id + flags come from the GLM-5.2 model card; verify before running.)
  3. Get the box's public URL (e.g. https://<host>:8000/v1) and keep it firewalled to your IP.
  4. Send me the base URL and the secret. I point LiteLLM at it in config.yaml; the reviewer role becomes openai/GLM-5.2 with api_base set. No other code changes; that's the point of the LiteLLM seam.
Never paste the GPU box's SSH key or cloud-account credentials to me. I only need the inference endpoint URL and its API secret.

Kalshi account & API REQUIRED FOR TRADING

Needed even in paper mode: the council reads live Kalshi prices to make realistic simulated decisions. No real orders are placed until you explicitly flip to live.

  1. Create and verify a Kalshi account (KYC required; US-regulated exchange).
  2. Generate API credentials (Kalshi uses an API key ID + an RSA private key for request signing). Download the private key file; it's shown once.
  3. For paper mode we only call read endpoints (markets, prices, order book). Do not fund the account yet.
  4. Put the key ID + the path to the private key file in ~/council/.env. Keep the key file chmod 600 and outside git.
  5. (Live only, later) Only once paper results justify it: fund with an amount you can afford to lose, and we enable the guarded execution layer with hard caps + a kill switch.
Check Kalshi's terms on automated/algorithmic trading before going live; confirm bots are permitted on your account type.

Before real money touches the floor

  • Weeks of paper-mode P&L showing a real, fee-aware edge, not a few lucky days.
  • Hard caps wired: max position size, daily-loss halt, total bankroll cap, kill switch.
  • Human approval on every live order, at least at first.
  • Keys stored as chmod 600 files, never pasted into chat, never committed.
  • The overnight-suspend issue on this machine resolved; a trading loop must not die mid-position.
